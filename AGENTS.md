## Critical Architecture Rules

- **RAW-first invariant**: raw Telegram messages are ALWAYS saved to SQLite BEFORE any parsing/classification. Never change the order in `collectors/dvinchik_collector.py`.
- **FilterEngine is Telegram-free**: `services/filter_engine.py` takes only `Profile + AppConfig`. Never import Telethon types there.
- **Deterministic scoring is Telegram-free**: `services/decision_service.py`, `services/profile_normalizer.py`, `services/feature_extractor.py`, `services/score_engine.py` never import Telethon. Work only with Profile/str and Config.
- **Deterministic scoring (Stage 8)**: Scoring is a pure rule engine, no LLM/CLIP/network. **Exception (2026-10-22, by owner's request): photo vice check** — `services/photo_vice.py` (CLIP zero-shot, local CPU, config `photo_check`, default off) may turn a LIKE into DISLIKE via `DecisionService.apply_photo_vice` (reason `PHOTO_VICE:*`); only LIKE candidates are checked, right before the auto-action, errors never change the decision. Tests: `tests/test_photo_vice.py`. **Photo taste model** (`services/photo_taste.py`, shared `services/clip_encoder.py`, config `photo_taste`): every new card with photos is scored in the background (`DvinchikCollector._schedule_photo_shadow`, capped queue) → table `photo_scores`. `mode: shadow` (default) — verdict only; **`mode: decide` (owner-approved 2026-10-23, enabled on the server)** — `_apply_photo_taste` turns the decision into LIKE (score ≥ top-`like_share` threshold) / DISLIKE with reason `PHOTO_TASTE:*`, unless text bans/strong plus win (`DecisionService.photo_taste_applies`); video cards are scored by the video preview frame; no verdict → the profile's stored embedding from a previous showing; nothing → old text rule. Results of finished shadow tasks are kept in `_photo_shadow_results` (a task may finish before the decision is made). The vice check reuses the card's shadow result (no second CLIP run — CPU ~1.5 s/photo, reaction latency matters). Weights JSON lives on the server only (`data/ml/taste_model.json`, trained on the owner's /rate labels). Tests: `tests/test_photo_taste.py`. **Active learning**: background backfill in the bot (`run_photo_backfill`: unrated first, photos from `media/` cache or downloaded by the receiving account) fills `photo_scores` + `photo_embeddings`; `/rate` queue puts the most uncertain (score ≈ 0.5) first with every 5th from the normal order; `scripts/train_photo_taste.py` retrains from `photo_embeddings` × `photo_ratings` and replaces the model JSON only if OOF AUC is not worse; the bot hot-reloads the JSON (mtime, 30 s). `DecisionService.evaluate()` runs for **ALL** filter results (PASS/REJECT/REVIEW); the decision is derived internally. Rules live ONLY in `config/preferences.yaml`; never hardcode in `decision_service.py`. Missing/unknown info → REVIEW, never DISLIKE (`NO_HARD_NEGATIVE_MUST_NOT_BECOME_DISLIKE`). Scoring version `deterministic-v2`. Decision на основе **информативности**: `informative + clean → LIKE` (достаточно значимых слов `>= 10` ИЛИ найден позитивный признак; `score_engine` считает `informative`/`meaningful_words`); черновые/короткие, но чистые → REVIEW. `like_threshold`/`review_threshold` в конфиге остались, но для решения инертны. **DecisionService НЕ выполняет действий** — только возвращает LIKE/REVIEW/DISLIKE (+`informative` для слоя действий).
- **AI scoring gated by PASS**: Legacy only. In the current collector, `DecisionService` evaluates every profile regardless of filter result. On the auto account, filter-level REJECT/REVIEW still auto-sends `👎` (via `auto_engine.maybe_act(AIDecision.DISLIKE)`) so Leo's stream never blocks; the profile + filter result remain in DB. This means: non-PASS filter results get `DISLIKE` recorded in `auto_actions_log` with the filter decision as reason.
- **Bot errors are reported** (`collectors/error_reporter.py`): every ERROR log record → `app_state.bot_error` (site popup `#bot-error`) + Telegram to the owner's twin account via `notify_owner` (same error ≤ 1 per 10 min). Photo steps `_apply_photo_taste`/`_apply_photo_vice` are wrapped and must never raise into the auto-action (prod 2026-10-23: an UnboundLocalError there stopped the feed). Tests: `tests/test_error_reporter.py`.
- **AI errors must not break Collector**: All AI calls are wrapped in try/except. RAW messages are never lost.
- **Preferences layer (SKIP/LIKE)**: User's calibration rules (`app/preferences.py` → `PreferencesEngine`) live ONLY in `config/preferences.yaml` (live, gitignored) / `config/preferences.example.yaml` (committed). Never hardcode rules in `services/decision_service.py` — it only applies them. SKIP → hard DISLIKE; LIKE-factor → a DISLIKE is lifted to REVIEW (profile not lost). Thresholds 0.75/0.50 unchanged.
- **`filters/` was deleted during simplification** — the placeholder package is gone. Actual filter logic lives in `services/filter_engine.py` and `services/filter_service.py`. Do not recreate the placeholder.
- **Web UI = один экран (Stage 9)**: `/` и `/chat` (`web/blueprints/chat.py`, `web/templates/app.html`) — **лента-зеркало чата** (НЕ карточки и НЕ чат-пузыри: одна колонка, строки `.row` = grid «время + содержимое», `data-decision`/`data-name` для фильтра и поиска) + выбор режима + ⚙-drawer настроек. Legacy-роуты `/dashboard`, `/settings`, `/profiles/<id>(/action)` → 302 на `/`; legacy API `/dashboard/action/<id>/<action>` оставлен. Удалены `captchas.py` blueprint, шаблоны `chat/dashboard/settings/profile/captchas.html`, `partials/chat_feed.html`, `partials/profile_cards.html`, `partials/pagination.html`, `static/css/style.css`. Новая статика — `static/css/app.css` + `static/js/app.js`. Аккаунт-исполнитель перенесён из drawer в **топбар** рядом с выбором режима (`#account-form` в `web/templates/app.html`, авто-сабмит при выборе + кнопка `ОК` как fallback без JS); drawer содержит только фильтры и `SKIP/LIKE`-предпочтения.

- **Два вида ленты** (`#view-seg`, `?view=direct|smart`, запоминается в `session['feed_view']`): «Прямой» — инварианты ниже; «Улучшенный» — `SyncDB.get_decision_feed` (только LIKE/DISLIKE из `auto_actions_log` + причины из `ai_decisions` на момент действия, шаблон `partials/app_decisions.html`, та же сетка `.row`). Коды причин переводит ТОЛЬКО `services/reason_labels.py` (`describe_reasons`) — и для сайта, и для TG (`AutoActionEngine._format_reason`); новые коды причин добавлять туда. Тесты: `tests/test_web.py::TestDecisionFeed`, `TestReasonLabels`.
- **Лента = прямое дублирование Telegram-чата** (инвариант): `/` читает **только** `raw_messages` (RAW-first: там весь чат — входящие Leo + наши исходящие) и показывает ОДНО сообщение = ОДНА строка в хронологическом порядке. `sent_messages` / `auto_actions_log` в ленту **НЕ подмешиваются** — это журналы действий, а не события чата: их `telegram_message_id` указывает на карточку анкеты, а не на сообщение-реакцию (из-за этого лента съезжала на соседнюю анкету). Детали: `web/db.py` (`get_chat_feed`, `_feed_item`, `_profile_for_message`), README → «Лента = прямое дублирование Telegram-чата».
  - **Наши исходящие пишет и сам движок** (`AutoActionEngine._persist_outgoing`, вызывается из `_send`): коллектор ловит исходящие эхо-событием Telethon (`NewMessage(outgoing=True)`), но оно приходит не всегда (прод-замер 2026-10-19: 311 действий за день, лишь 7 исходящих в `raw_messages`) — 👎/❤️/кнопки/«Берем)» пропадали из ленты и порядок «карточка → реакция → сообщение» разъезжался. Движок знает `send_message(...).id` и сохраняет сообщение сам (`is_outgoing=True`, `account_session`); дубликат с эхо-событием схлопывает UNIQUE-индекс `raw_messages` (INSERT OR IGNORE). Уведомления владельцу (`_notify*`) шлются напрямую `client.send_message(target=…)`, мимо `_send`, поэтому в ленту Leo не попадают.
- **Лента фильтруется по аккаунту-исполнителю — СТРОГО**: `raw_messages.account_session` (миграция `_ensure_raw_account_session_column`, ставит коллектор при сохранении) + `get_chat_feed(..., account_session=...)` — показываем строки РОВНО выбранного аккаунта (legacy `''` НЕ подмешивается; иначе соседний аккаунт «протекает» в ленту). Иначе чаты двух аккаунтов (один `chat_id`, разные диапазоны message id) перемешиваются. **Парсинг тоже строго на аккаунт**: дедуп (`_dedup`), лок чата (`_chat_locks`), `_pending_profiles` и таблица `chat_context` (`PRIMARY KEY (account_session, chat_id)`, миграция `_ensure_chat_context_account_session`) ключуются парой `(account_session, chat_id)` — у аккаунтов своё пространство message id в одном чате, и MEDIA_ONLY одного аккаунта не должен привязываться к карточке другого. Фото качается ТОЛЬКО аккаунтом-получателем (`web/photos._ordered_clients` — без fallback на чужой аккаунт). **Legacy-разметка**: оба аккаунта слушают ОДИН чат Лео, поэтому до появления колонки в `raw_messages` лежали сообщения обоих сразу (id-пространства: `dvai` ~708k, `dvai_2` ~22k) — «супер-чат», не совпадающий ни с одним TG. `Database.backfill_raw_account_session(sender_to_session)` (вызывается из `main.py` после `get_me()` по каждому клиенту, гейт `len(clients) > 1`) размечает историю: исходящие — по `sender_id` (= user id аккаунта), входящие — по ближайшему диапазону id исходящих аккаунта (разрыв огромный → однозначно).
- **Сверка ленты с Telegram**: `DvinchikCollector.run_history_sync()` (таск из `main.py`) раз в 60 с вызывает `sync_chat_history()` — по каждому аккаунту последние 100 сообщений чата Leo → `INSERT OR IGNORE` в `raw_messages` (+ `mark_raw_processed`, pipeline не запускается). Сообщения моложе 120 с (`HISTORY_SYNC_MIN_AGE_SEC`) НЕ трогать — их отдаёт pipeline живой хендлер; дубликат на INSERT лишил бы карточку обработки. Polling-перерисовка — одним запросом `/chat/feed?page=1&pages=N`; время в ленте переводится в местное на клиенте (`localizeTimes`).
- **Пагинация ленты — в SQL**: `ORDER BY telegram_message_id DESC, id DESC LIMIT/OFFSET` (нативный порядок чата Telegram), `total` считает те же непустые строки, что и страница. На странице — от новых к старым (свежее СВЕРХУ, под панелью управления); «Показать более ранние» — под лентой, дописывает вниз. **Сигнатура polling (`get_chat_signals`) — на аккаунт**; обновление перерисовывает все загруженные страницы (1..N), не схлопывая историю.
- **`raw_messages.is_outgoing`**: колонка (`INTEGER DEFAULT 0`) + миграция `_ensure_raw_is_outgoing_column` с backfill `WHERE sender_id <> chat_id`. Ставится перехватчиком исходящих (`DvinchikCollector._handle_outgoing_message`) — иначе наш собственный `👎` рисуется в ленте как входящее сообщение от Leo. Не сдвигай её в `SCHEMA`/`save_raw_message` так, чтобы сломать позиционные вызовы (все вызовы — keyword).
- **`idx_raw_unique` включает аккаунт и направление**: `UNIQUE(account_session, chat_id, telegram_message_id, is_outgoing)`. Пространства id входящих и исходящих пересекаются, и у аккаунтов свои пространства; старый `UNIQUE(chat_id, telegram_message_id)` **молча отбрасывал** наши исходящие на `INSERT OR IGNORE` (сырые записи всех реакций). Индекс пересоздаётся при старте (`DROP` + `CREATE`); `account_session` и `is_outgoing` мигрируются ДО индекса в `Database.connect()`.
- **Лента — только чат Leo**: роуты передают `chat_id=_leo_chat_id(config_path)` в `get_chat_feed`/`get_chat_signals` (из `dvinchik.chat_id`). В `raw_messages` есть legacy-сообщения групп с бо́льшими id — без фильтра они перемешивались с анкетами (регресс-тест `test_feed_shows_only_leo_chat`).
- **Альбом анкеты — одна строка**: `SyncDB._group_albums` склеивает фото без текста той же анкеты (`profile_id`) в `photos` предыдущей входящей строки; шаблон рисует `item.photos`. Склейка идёт в хронологическом порядке, ПОТОМ лента разворачивается (свежее сверху) — не менять порядок этих шагов, иначе подпись отвалится от альбома (`test_album_whole_in_newest_first_feed`). Страница открывается сверху.
- **Имя сессии клиента — из `main.py`, не по позиции** (`DvinchikCollector(..., client_sessions=...)`, `_resolve_client_sessions`, `_clients_for_session`): в `clients` попадают только вошедшие аккаунты, поэтому позиция клиента может не совпадать с позицией в `telegram.accounts`. Раньше при невошедшем первом аккаунте второй получал его имя (сообщения и действия — не тому аккаунту). Без `client_sessions` (тесты) — прежняя эвристика по `telegram.accounts` (`TestClientSessions`).
- **Штатные сообщения Leo (`✨🔍`, «Отправь текст…») пишутся в лог как DEBUG**, а не WARNING «Unknown message format» (`ROUTINE_LEO_TEXTS`, `_is_routine_leo_text`); классификация и обработка не меняются.
- **Пустые сообщения в ленте не показываются** (нет текста и медиа — кнопки меню). Фото-сообщение рисуется миниатюрой: `profile_id` резолвится через `profile_messages` (маршрут `photos.serve_photo`).
- **Карточек/бейджей/форм в ленте нет** — анкета показывается теми же сообщениями, что в Telegram. `data-decision`/`data-name` остаются скрытыми атрибутами строк для клиентского фильтра/поиска. Ручные маршруты `/chat/profile/<id>/<action>` и блок «Капчи ждут ответа» остаются рабочими.
- **Разметка внешности (`/rate`)**: `web/blueprints/rate.py` + `templates/rate.html` + `static/js/rate.js`, кнопка `#rate-open` в топбаре главной. Владелец оценивает ТОЛЬКО фото анкеты (без текста) → таблица `photo_ratings` (`profile_id` PK, `LIKE`/`DISLIKE`/`SKIP`, повтор перезаписывает, undo удаляет). Это обучающие метки для фото-модели вкуса — на решения/действия бота НЕ влияют. Фото — с одного аккаунта-получателя (`SyncDB._rating_photos`, последний показ), только `account_session <> ''`; анкеты с фото в кэше `media/` идут первыми (`get_rating_queue(prefer=...)`), чтобы разметка не нагружала Telegram. Проверка «фото» в `_RATE_PHOTO_SQL` — только с `rm.account_session IN (pm.account_session, '')`, иначе мимо `idx_raw_unique` и полный скан `raw_messages` (прод 7.9 с, регресс-тест `test_photo_query_uses_raw_index`). На телефоне — Tinder-свайп (`rate.js`: pointer events на `#rate-card`, тап по краю листает фото). Очередь в браузере дедуплицируется по `seen` (НЕ обрезать список исключений так, чтобы из него выпадала очередь — прод-баг 2026-10-22, анкеты шли по второму кругу); клавиши — `window` capture + игнор `e.repeat`. Тесты: `tests/test_web.py::TestPhotoRating`.
- **Тема**: палитра — CSS-переменные (`:root` тёмная, `[data-theme="light"]` светлая), переключатель `#theme-toggle` в топбаре + `localStorage`, применение до первой отрисовки — `web/templates/partials/theme_boot.html` (подключён в `base.html` и `login.html`). За пределами палитр сырых цветов в `app.css` быть не должно (`TestTheme`), иначе в светлой теме тёмные пятна.



- **`config/config.yaml` is gitignored** (contains API keys, phone, proxy creds). Only `config/config.example.yaml` is committed. Never commit real secrets.

## Code Conventions

- **Python 3.12+** — `StrEnum`, `X | Y` union syntax, lowercase `list[str]` generics.
- **`from __future__ import annotations`** in every module.
- **Type hints on all function signatures** including return types.
- **Private attributes** use underscore prefix: `self._client`, `self._db`.
- **Docstrings and comments in Russian**, code identifiers in English.
- **`TYPE_CHECKING` guard** for heavy imports (avoids circular deps).
- **Pydantic v2** models — use `field_validator`, not `validator`.
- **Loguru** for logging (not stdlib logging). Rich for console output.

## Gotchas

- **Dual FilterResult types**: `models/raw.py` has `FilterResult` (FILTER_MATCH/FILTER_NOT_MATCH) used by the parser. `models/filter.py` has `FilterResult` (PASS/REJECT/REVIEW) used by the filter engine. They serve different layers.
- **`FilterResult` in `models/raw.py`** uses Pydantic `StrEnum` named `FilterResult` — do not confuse with `models/filter.py`'s `FilterResult` dataclass.
- **SQLite WAL mode** + foreign keys explicitly enabled via PRAGMA. Schema is idempotent (`CREATE TABLE IF NOT EXISTS`).
- **Windows-specific**: `run.bat` sets `chcp 65001`, `PYTHONUTF8=1`, `PYTHONIOENCODING=utf-8`. `main.py` also forces UTF-8 on stdout/stderr.
- **Banner version** (`banner.py`) is synced to `"0.7"`.
- **Chat ID 1234060895** is the Dayvinchik bot default, hardcoded in `config/config.example.yaml`.
- **`proxy/`** contains vendored xray-core binaries and real VLESS config — do not commit credential changes.
- **Human decisions append-only**: `human_decisions` history is never UPDATE/DELETE. `UNIQUE(ai_decision_id)` — one review per AI evaluation. Latest human decision by `created_at`.
- **`get_profile_by_id` returns dict** (not `Profile` object) — in `_render_profile` use `profile['id']`, not `profile.id`.
- **DB thread leak in tests**: any test that opens a `Database` must close it (fixture teardown). A leaked aiosqlite thread prevents the pytest process from exiting (hang).
- **ReviewBot / ReviewService / AnalyticsService удалены** (2026-10-21): бот рецензий отвечал на `/stats`, `/review`… любому пользователю Telegram. Не возвращать. Ручные решения — `manual_review` (журнал) и кнопки сайта (`human_decisions`).
- **Decision != Action (§30)**: `DecisionService`/`AIDecision` — только LIKE/REVIEW/DISLIKE, Telegram-free. Telegram-действия — `models/action.py` (`ActionPolicy`: NO_ACTION/LIKE_AND_MESSAGE/DISLIKE_ONLY — **LIKE_ONLY удалён**: обычного лайка без сообщения больше нет) + `services/action_policy.py` (`ActionPolicyResolver`), которые тоже Telegram-free; их потребляет `AutoActionEngine`. Не смешивать Decision и Action.
- **`AIDecisionResult.informative/meaningful_words`**: проставляются из `ScoringResult` в `DecisionService.evaluate_profile`; коллектор передаёт `decision.informative` в `maybe_act` (в политику уже не влияет: LIKE всегда LIKE_AND_MESSAGE).

## Project Stage

Currently at **Stage 8 (deterministic scoring)** + **Stage 8.5 (like analytics)** on top of **Stage 7 (SEMI_AUTO)**. See `Roadmap.md` for roadmap. DecisionService computes LIKE/REVIEW/DISLIKE via a deterministic rule engine (`profile_normalizer` → `feature_extractor` H01–H09/P01–P04 → `score_engine`), rules from `config/preferences.yaml`; never LLM/CLIP. **Decision != Action (§30)**: `DecisionService` возвращает только LIKE/REVIEW/DISLIKE и НЕ знает о Telegram; что именно слать в чат (❤️ / 👎 / +«Берем)») решает слой действий (`models/action.py` `ActionPolicy` + `services/action_policy.py` `ActionPolicyResolver`). LIKE → **только** `LIKE_AND_MESSAGE` (`💌 📹 🎤` + «Берем)», **❤️ не шлётся**): обычного лайка без сообщения больше нет (`LIKE_ONLY` удалён), выключенный `like`/`like_message` → NO_ACTION. В SEMI_AUTO коллектор шлёт авто-действия через `AutoActionEngine` на авто-аккаунте: LIKE→цепочка `💌 📹 🎤` → «Берем)»; DISLIKE→`👎`; **AI REVIEW→ не действует сам** (уведомляет владельца — см. Manual Review), rate-limited (`interval_sec`, default 2 s). `config.project.mode` гейтит авто-действия (OBSERVE → no actions). Active stream: `collector.start_auto_stream()` processes the already-displayed active profile or presses «Смотреть анкеты». Do not implement full AUTO / dialog manager until explicitly instructed.

## Auto-Actions (Stage 7)

- Live in `collectors/auto_action.py`: `AutoActionEngine(client, config, mode, chat_id, notify_client=None, db=None)`. `db` (Database) нужен, чтобы при уведомлении владельцу пересылать **все** фото анкеты (PROFILE + связанные MEDIA_ONLY из `profile_messages` через `get_profile_messages(profile_id)`), а не только одно PROFILE-сообщение. Без `db`/`profile_id` — прежнее поведение (один `message_id`); ошибки БД ловятся.
- Gate: `enabled` only when mode ∈ {SEMI_AUTO, AUTO} AND `auto_actions.enabled` AND a client exists (matched via `account_session` to `telegram.accounts`/`self._clients` by index).
- `maybe_act(decision, ..., informative=...)`: Decision != Action (§30) через `ActionPolicyResolver`. DISLIKE→`👎`, **AI REVIEW→ не действует сам** (возвращает `"REVIEW"`, уведомляет владельца — см. Manual Review ниже), disabled→`GATE`. LIKE → **только** `LIKE_AND_MESSAGE` (цепочка «Берем)», `LIKE_ONLY` удалён): `💌 📹 🎤` → (Leo: «Отправь текст, видео или голосовое…») → «Берем)»/«беру)». **❤️ НЕ шлётся** (упирается в дневной лимит «Слишком много ❤️»): `maybe_act` сразу отправляет кнопку композера `MESSAGE_BUTTON_TEXT` (стадия `AWAIT_PROMPT`); не удалось — цепочка снимается. Повтора по «Лайк отправлен» больше нет (ветка `AWAIT_LIKE_ACK` удалена 2026-10-21 как недостижимая). Отправлять надо **всю строку кнопок** `💌 📹 🎤` — одиночный `💌` Leo не распознаёт (прод tm=722860/722895). Цепочка живёт в `_pending_chains` и прогрессирует из `step_pending(text, chat_id)` (вызывается коллектором на входящих НЕ-PROFILE сообщениях чата Дайвинчика на авто-аккаунте); Финальный «Берем)» записывается в БД как действие `MESSAGE`. **Текст в композер шлётся вне общего rate-limit** (`_send_composer_text`, свой лок + `_COMPOSER_SEND_GAP_SEC`=1.5 с): прежний общий `interval_sec` (10 с) успевал вставить между лайком и сообщением `👎` на следующую карточку, и Leo отвечал «Сообщение слишком короткое. Введите сообщение заново.» **Пока композер открыт, реакция на новую карточку откладывается** (`_has_open_composer` → `_defer_reaction`, `maybe_act` → `"DEFERRED"`), в слоте держится ПОСЛЕДНЯЯ карточка (Leo показывает одну активную); сброс — при закрытии цепочки (`_flush_deferred` из `step_pending` шага 3/3, запись в `auto_actions_log` делает сам движок, т.к. collector при DEFERRED молчит) либо по таймауту `_COMPOSER_WAIT_SEC`=20 с (цепочка снимается через `_drop_stale_chains`, лента идёт). Фильтровые не-PASS (REJECT/REVIEW) на авто-аккаунте по-прежнему шлют `👎` через `maybe_act(AIDecision.DISLIKE)` — иначе Leo ждёт реакцию и лента замирает; профиль и фильтр-решение остаются в БД.
- **Гейт «реакция — в СВОЮ карточку» (Stage 7.9)**: Leo держит ОДНУ активную карточку и принимает `❤️`/`👎` только пока она на экране, а ленту листает САМА (~каждые 2–10 с). Прод-замер: при `interval_sec = 10 с` лаг карточка→действие был 10–30 с и **54 из 60 действий попали на ЧУЖУЮ анкету** (дизлайк подходящей / лайк неподходящей). Теперь: `AutoActionEngine.note_card(chat_id, message_id)` (номер только растёт; сбрасывается в `swap_client` — у аккаунтов разные пространства id) вызывается коллектором из `_handle_new_message` **сразу после RAW-save, до worker'а** (иначе отставание pipeline не видно), для PROFILE-сообщений авто-аккаунта; `maybe_act` при `is_stale_card()` возвращает `"STALE"` и НИЧЕГО не отправляет (и в `auto_actions_log` не пишется) — лучше пропуск, чем промах. Гейт стоит ПЕРЕД composer-отложкой, поэтому устаревшая карточка не попадает и в `_deferred` (тот при сбросе отбрасывается тем же гейтом). `message_id is None`/неизвестная карточка — гейт выключен (ручная отправка из Web UI, тесты). Точность страхует малый `interval_sec` (default **2 с**, был 10).

LIKE и MESSAGE — **независимые** действия (§30): на одну карточку может быть LIKE и MESSAGE, но каждый вид — не более одного раза. Повторная карточка той же личности (новый `telegram_message_id` в ленте) получает реакцию снова, чтобы лента не замирала при повторах Leo. `auto_actions_log` хранит `telegram_message_id` (partial unique index `chat_id`+`telegram_message_id`+`action` WHERE `telegram_message_id IS NOT NULL`), `UNIQUE(profile_id)` убран; `record_auto_action` обновляет статус профиля `LIKED`/`DISLIKED` только для LIKE/DISLIKE (MESSAGE статус НЕ меняет). Миграция старой схемы — полное пересоздание таблицы с переносом записей (SQLite не умеет DROP CONSTRAINT) / пересоздание unique-индекса.
- **Уведомления владельцу НЕ дублируются**: реакция (`❤️`/`👎`) шлётся Leo на каждую карточку (feed не замирает), но пересылка владельцу (`_notify`/`_notify_needs_action`) выполняется ТОЛЬКО для первого авто-действия профиля — гейт `_has_prior_action(profile_id)` через `db.has_auto_action(profile_id)`. Иначе повтор одной анкеты заваливает владельца пересылками всей её истории («несколько анкет разом»). Ошибка БД при проверке → fail-open (уведомление всё равно уходит).
- **Пересылка владельцу фильтруется по аккаунту (прод-баг 2026-10-19)**: `_profile_message_ids` берёт из `profile_messages` только id с `account_session` текущего аккаунта-исполнителя (строки с пустой сессией — legacy — оставляем). Причина: у каждого аккаунта СВОЁ пространство `telegram_message_id` в одном чате Leo; если одну анкету видели оба аккаунта (`dvai` ~739k, `dvai_2` ~30k), в БД накапливались id обоих, и `forward_messages(..., from_peer=Leo)` с чужим id резолвился Telethon'ом в ПОСТОРОННИЕ сообщения — владельцу переслало чужие переписки (id 739500 из `dvai` + 30297 из `dvai_2`). `AutoActionEngine.account_session` задаётся при создании (`_build_auto_engine`) и при `swap_client(..., account_session=...)` (смена аккаунта из Веба/`switch_auto_account`).
- **Резолв ЛЕО-чата**: `AutoActionEngine.ensure_peer()` сканирует диалоги авто-аккаунта и кэширует сущность чата (ЛЕО-чат — `PeerUser`, у каждого аккаунта свой access_hash; без кэша `send_message` падает «Could not find the input entity»). Вызывается из `_send` и `start_auto_stream`. Если чата нет в диалогах — явный WARNING «открой Дайвинчика (Leo) с этого аккаунта» и действий нет.

## Manual Review (Stage 8)

- Логика в `services/manual_review.py` (Telegram-free): `ManualReviewRecorder(db, path, enabled, file_format)` — фиксирует РУЧНОЕ решение владельца по REVIEW-анкете в файл (`data/reviews/review_log.json` или `.md`). `classify_outgoing(text)`: `❤️`→LIKE, `👎`→DISLIKE, иначе MESSAGE.
- Сценарий: детерминированный scoring выдал REVIEW (бот «не справляется»). `AutoActionEngine.maybe_act(REVIEW)` НЕ шлёт авто-`👎` (`_notify_needs_action`: пересылает карточку владельцу и пишет «Нужно твоё решение»), ждёт ручного действия. Анкета остаётся активной в ленте.
- Владелец действует с того же аккаунта, под которым слушает collector (тот же, что `dvinchik.chat_id`). Исходящее действие перехватывается в `_handle_outgoing_message` → `_maybe_record_manual_review`: через `get_chat_profile_context(chat_id)`/`_pending_profiles` берёт «текущую» анкету чата и, если последнее AI-решение == REVIEW, вызывает `manual_review.handle_outgoing(...)` → запись в файл.
- Только активная REVIEW-анкета: бот и сам шлёт `❤️`/`👎` (LIKE/DISLIKE), но recorder записывает лишь когда последнее AI-решение профиля == REVIEW → ложных записей нет.
- Проводка: `main.py` создаёт `ManualReviewRecorder` (гейт `config.manual_review.enabled`) и передаёт в `DvinchikCollector(..., manual_review=...)`. Конфиг — `manual_review: enabled / file / format (json|md)` в `config.yaml`/`config.example.yaml`. Ошибки файла/БД не ломают перехват исходящих (RAW уже сохранён).

## Like Analytics (Stage 8.5)

- **Цель**: статистика «что написал при лайке и ответила ли девушка» — какие тексты сообщений работают лучше (конверсия в ответ) и каких девушек чаще лайкают.
- **Результат фиксируется на КАЖДЫЙ лайк**: таблица `like_outcomes` — по лайку (авто/ручной) хранит `message_text` (содержание сообщения, '' если без текста) и `responded` (0/1) — лайкнула девушка в ответ или нет. Рядом с каждым лайком (`LIKE` в авто-журнале или ручном `sent_messages`) заводится строка через `record_auto_action`/`record_sent_message`; `MESSAGE` прикрепляет текст к лайку на ту же карточку/время; взаимный лайк (`record_match_response`) проставляет `responded=1` по всем висящим лайкам профиля (только `rejected=0`). Идемпотентность — UNIQUE(`source, chat_id, like_tm_id`). Бэкфилл старых лайков из `auto_actions_log`∪`sent_messages` в `_ensure_like_outcomes` (INSERT OR IGNORE).
- **Отклонённые лайки (лимит Leo)**: если Leo на ❤️ отвечает «Слишком много ❤️ за сегодня» (детектор `DvinchikParser.is_like_rejection` — маркеры «слишком много»/«закончились»/«лимит»/«позже» + предмет «❤/💌/лайк/сообщени»), коллектор вызывает `Database.mark_like_rejected(chat_id)` — свежий неотклонённый лайк чата (окно 120 c) помечается `rejected=1` и из аналитики (`get_top_liked_profiles`, флипы `responded`) исключается. Повторные отказы подряд помечают лайки по очереди. Само сообщение трактуется как SERVICE. Колонка `rejected` мигрируется в `_ensure_like_outcomes` (ALTER ДО создания `idx_like_outcomes_rejected` — в top-SCHEMA его нет, иначе legacy-базы падали бы на executescript).
- **Лимит ❤️ исчерпан → пауза до 07:00 (Stage 8.5.2)**: того же отклонения мало для аналитики — раньше бот продолжал слать ❤️ (все отклонялись) и открывал композер «Берем)» после отклонённого лайка (Leo отвечал «Нет такого варианта ответа»). Теперь `DvinchikCollector._process_message` при `is_like_rejection` зовёт `AutoActionEngine.handle_like_rejection(chat_id)`: (1) помечает `likes_exhausted_until` = ближайшие **07:00 локального времени** (`_compute_like_limit_reset`), сохраняет в **`app_state`** (key/value, `Database.set_state`/`get_state`/`delete_state` — переживает рестарт) **на аккаунт**: ключ `likes_exhausted_until:<account_session>` (`AutoActionEngine.like_limit_key`; `swap_client` на другой аккаунт сбрасывает и перечитывает состояние). Прод-баг 2026-10-21: ключ был общий — лимит dvai_2 блокировал лайки на dvai. Отказ, пришедший на НЕ-исполнителя (ручные лайки), лимит исполнителя не трогает; (2) `abort_like_chains(chat_id)` снимает незавершённые цепочки «Берем)» и отложенную реакцию (композер больше не открывается); (3) **один раз** уведомляет владельца (`notify_like_limit`, гейт на переходе «было не исчерпано»). В `maybe_act` при `policy == LIKE_AND_MESSAGE` и `likes_exhausted()` возвращается `"LIKE_LIMIT"` — ❤️ и «Берем)» НЕ шлются, а **👎 продолжает уходить** (иначе лента Leo замирает). Состояние лениво подгружается из БД (`_ensure_like_limit_loaded`). Тесты: `tests/test_auto_action.py::TestAutoActionLikeLimit`, `tests/test_collector.py::TestCollectorActiveCard::test_like_rejection_marks_likes_exhausted`, `tests/test_analytics.py::TestAppState`.
- **Два источника сообщений при лайке**:
  1. Авто-«Берем)» (цепочка LIKE_AND_MESSAGE) — текст пишется в `auto_actions_log.message_text` при `action='MESSAGE'` (из `like_message.text`; `record_auto_action(..., message_text=...)`). Колонка добавлена миграцией `_ensure_auto_actions_message_text`.
  2. Ручные действия владельца — фиксируются в `sent_messages` (`source='manual'`) с классификацией `action`: «❤️»→**LIKE** (сам лайкнул), «👎»→**DISLIKE**, остальные тексты→**MESSAGE**. Запись — в `_handle_outgoing_message` → `_maybe_record_sent_message`. Исходящие с авто-аккаунта пропускаются ТОЛЬКО когда авто-действия реально включены (`auto_engine.enabled`, SEMI_AUTO/AUTO) — они уже в `auto_actions_log`; в OBSERVE авто ничего не шлёт, поэтому любой исходящий (в т.ч. с авто-аккаунта) = ручное действие владельца и записывается. Кнопки/навигация Leo отсекаются через `is_manual_message_excluded` (`MANUAL_MESSAGE_EXCLUDE` + `MANUAL_MESSAGE_EXCLUDE_FRAGMENTS` + нумерованные кнопки меню «1 🚀»/«1 👍» по regex, тексты короче 2 символов). Профиль привязывается по «текущей» анкете чата (`get_chat_profile_context`/`_pending_profiles` → `Database.resolve_profile_by_message`).
- **Сигнал ответа** — взаимный лайк: MATCH-сообщение «Начинай общаться 👉 [Имя]» → `Database.record_match_response(name, chat_id, tm_id, telegram_username=...)`. Привязка к профилю по имени (`_resolve_profile_by_name`): регистронезависимо по-настоящему (Python `lower`), приоритет — профили со свежими записями `auto_actions_log`∪`sent_messages`. Дубликаты на карточку отсекаются UNIQUE-индексом `(chat_id, telegram_message_id)` (INSERT OR IGNORE). Заодно проставляет `responded=1` в `like_outcomes`.
- **Отчёты** (Telegram-free, `Database`): `get_message_response_stats()` — по каждому тексту `sent` (уникальных профилей) / `responded` / `rate`; `get_top_liked_profiles(limit)` — топ по лайкам (из `like_outcomes`, авто∪ручные) + ответили ли + последнее сообщение при лайке. Команды ControlBot `/msgs` и `/top` (+ inline-кнопки «💬 Сообщения»/«💖 Топ лайков»).
- **Правила**: аналитика read-only и не влияет на действия (LIKE/MESSAGE всё равно шлются); ошибки БД в записи ответов/исходящих не ломают pipeline (RAW уже сохранён).

## Debug Console (Stage 9)

- **Цель**: один экран для диагностики «почему бот встал / почему анкеты в TG и на сайте расходятся» — без ssh и journalctl.
- **Источник логов**: `app/logging.py` держит кольцевой буфер `LOG_BUFFER` (`deque(maxlen=500)`) — sink `_buffer_sink` регистрируется в `setup_logging` (и лениво из `get_recent_logs`). Плюс stdlib→loguru перехват (`_InterceptHandler`, уровень `WARNING`), чтобы в буфер попадали ошибки сторонних библиотек (asyncio/telethon/werkzeug), которые Loguru сам по себе не видит. Формат записи: `{ts, level, no, name, message}`.
- **API**: `GET /chat/debug` (`web/blueprints/chat.py`) — `login_required`, JSON: `logs` (из `app.logging.get_recent_logs(limit, min_level)`) + `state` (`mode`, `account_session`, `stream_error`, `likes_exhausted_until`, `counts`, `signals`, `last_auto_actions`). Query: `limit` (1..500, default 200), `level` (минимальный уровень: `WARNING`/`ERROR`…). Данные состояния — из `web/db.py`: `get_debug_counts`, `get_debug_states`, `get_recent_auto_actions`.
- **UI**: кнопка `#debug-open` в топбаре (`web/templates/app.html`) открывает второй drawer `partials/app_debug.html` (`#debug-drawer`, `#debug-backdrop`, класс `.drawer--wide`) с блоком «Состояние» (`#debug-state`, `pre`) и списком логов `#debug-logs` (строки `.debug__log--<level>`, цвета — через переменные палитры). JS (`static/js/app.js`): `openDebug`/`closeDebug`, авто-обновление `refreshDebug` раз в `POLL_MS`, фильтр уровня `#debug-level`, Esc закрывает debug первым (иначе — drawer настроек). Рендер — только через `textContent`/DOM (без `innerHTML` из данных логов).
- **Тесты**: `tests/test_web.py::TestDebugConsole` (login-gate, форма payload, фильтр уровня, кнопка+drawer в шелле).

## Control Panel (Stage 7.5)

- Live in `telegram/control_bot.py`: `ControlBot(client, config, collector, db)`.
- Commands `/status /mode on|off /stream /recent /msgs /top /help` + inline-кнопки; принимаются ТОЛЬКО от `control.allowed_user_ids` (оба аккаунта-оператора: Бармалей `8525808108` + melancholic `1753676469`). **Только ВХОДЯЩИЕ ЛИЧНЫЕ сообщения, начинающиеся с `/`** (`events.NewMessage(incoming=True, func=is_private)`); не-команды игнорируются без записи в лог, логируется только имя команды — иначе бот отвечал на `/status` в любом чате владельца, а вся его переписка (и пересланные анкеты) попадала в лог и debug-консоль сайта (`TestControlBotPrivacy`).
- Регистрируется на ВСЕХ `telegram.accounts` (в `main.py` — цикл по `clients`); `config.control.enabled` гейтит регистрацию. Ответ шлётся с того же аккаунта, что получил команду (`event.client`).
- Runtime-переключение: `collector.set_mode(Mode)` → обновляет `AutoActionEngine.mode` на лету (гатег `enabled` пересчитывается) + `AppConfig.persist_mode()` записывает `project.mode` в `config.yaml` (переживает restart). `AutoActionEngine.mode` — сеттер.
- **Runtime-переключение аккаунта**: `collector.switch_auto_account(session)` → `AutoActionEngine.swap_client(client, notify_client)` (сброс peer-кэша и rate-limiter) + `AppConfig.persist_account_session()` в `config.yaml`. Веб-путь — `/settings/account` → `web.actions.set_account_sync` → тот же `switch_auto_account` + `start_auto_stream()` на новом клиенте. UI — выпадающий список аккаунтов в `/settings`.
- `collector.auto_engine()` — доступ к движку для панели; `collector.mode` — текущий режим.
